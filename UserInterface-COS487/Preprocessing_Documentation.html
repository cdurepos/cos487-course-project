Development Documentation

Introduction to Information Retrieval — Course Project, Part 1

Team: TheSearchParty Component: Data cleaning & tokenization Deliverables: Preprocessing.py, test_preprocessing.py Corpus: 34,308 arXiv papers Tests: 60 passing

This document records how the preprocessing component was built: what the data actually turned out to be, which design decisions followed from measuring it, what the unit tests caught, and the sequence of prompts and data queries used while developing it with an AI assistant. It is written so that a teammate building the TF-IDF or BM25 model can understand the inputs they are given without reading the source code first.

1Purpose

The retrieval models in this project score documents by comparing the words in a query against the words in a document. Before any scoring can happen, the raw corpus has to be turned into consistent lists of terms. That conversion is what this component does.

The corpus is arXiv paper text, which means it contains a large amount of material that is not natural language: LaTeX math, citation markers, URLs, and markup commands. If that content is left in, it becomes indexed vocabulary. Numbers from citation brackets become searchable "terms", fragments of equations inflate document lengths, and the term statistics that TF-IDF and BM25 depend on become noisier than they need to be. Cleaning is therefore not cosmetic — it directly changes the term frequency and document frequency values the models compute.

2The data

The corpus was measured before any code was written, and measured again during development. Every significant design decision in this component traces back to one of those measurements rather than to a guess. The queries used are reproduced in section 8.

Source schema

Each file in JSON Files/ has the same structure:

{
  "paper_id":  "2408.00001",
  "title":     "Replication in Visual Diffusion Models: A Survey and Outlook",
  "abstract":  "Visual diffusion models have revolutionized ...",
  "paragraphs": {
    "2408.00001_1": "Visual diffusion models have revolutionized ...",
    "2408.00001_2": "Visual diffusion models represent a significant ..."
  }
}

Two observations from this schema shaped the output design. First, the paragraph identifier already embeds the paper identifier (2408.00001_8 → 2408.00001), so no separate mapping file between paragraphs and papers is required. Second, the raw paragraph text remains available in these files, so the pipeline does not write a second copy of 2.3 million paragraphs to disk; anything that needs the original wording reads it back by identifier.

Two document collections

The project supplies two sets of relevance judgements, Study_paper_qrel.tsv and Study_paragraph_qrel.tsv, and requires separate result files at each level. The pipeline therefore produces two collections:

  • Paper level — one document per paper, built from title + abstract + every paragraph. The unit being judged is the whole paper, so the representation includes everything known about it.
  • Paragraph level — one document per paragraph, containing only that paragraph's text. The title is deliberately not prepended, because the paragraph qrel file judges the paragraph on its own merits, and injecting the title would let a paragraph inherit relevance from its paper.
Corpus defect found — duplicated abstracts

In a sample of 300 papers, 244 of them (81%) repeat their abstract word for word as the first paragraph; the full build later confirmed 29,936 of 34,308 (87%). The first version of the paper-level document concatenated the title, the abstract and every paragraph, which meant that in 87% of papers every abstract term was counted twice. Because the abstract contains the most topical vocabulary in a paper, this systematically inflated term frequency on exactly the words that describe what the paper is about, and it did so unevenly across the collection.

build_paper_text() now includes the abstract only when it is not already present as a paragraph.

Validation — no relevant document is destroyed by cleaning

All 728 paragraphs judged in Study_paragraph_qrel.tsv were checked against the pipeline. Every one of them exists in the corpus, and none of them clean to zero tokens. The cleaning rules therefore do not remove any judged-relevant document from reach, which would otherwise have placed a hard ceiling on achievable recall.

3Cleaning pipeline

The same function, preprocess(), is applied to documents and to queries. This is deliberate and is the most important structural decision in the component: if documents are cleaned one way and queries another, terms that should match never do, and the failure is silent — the system produces no error, it simply retrieves poorly.

  1. Remove inline LaTeX math — $x_i$ and similar expressions are symbol noise. The surrounding prose carries the retrievable meaning, not the equation.
  2. Remove LaTeX commands — stray \alpha, \textbf{...} would otherwise tokenize into fake terms such as alpha and textbf.
  3. Remove citation markers — [12] and [3, 4, 5] are reference pointers. Left in, the number 12 becomes an indexed term that can match queries for unrelated reasons.
  4. Remove URLs — link text contributes domain fragments, not topical content.
  5. Lowercase and tokenize — alphanumeric tokens are extracted, and hyphenated compounds such as text-to-image are kept as one token because they function as a single concept in this corpus.
  6. Drop stopwords and single characters — function words appear in nearly every document and carry almost no power to distinguish between them. Single characters are usually debris left behind by math removal.

Stemming is deliberately not in this list. It is applied later, for the reasons in the next section.

Design note — stopword list

The bundled stopword list is intentionally conservative. Frequent but meaningful terms such as data, model and method are not removed. Inverse document frequency already discounts terms that appear everywhere, so removing them by hand would discard information the weighting scheme handles better.

4Stemming is a load-time decision

The files written to processed/ contain cleaned but unstemmed words. This separates two operations that are easy to conflate:

  • Cleaning discards material that is not content — math, citations, URLs, function words. Nothing retrievable is lost, so it is safe to do once and reuse.
  • Stemming is lossy and is a retrieval decision rather than a data decision. Once code has been written to disk as cod, the original word cannot be recovered.

Keeping the saved files unstemmed has four concrete benefits:

  1. The stemming on/off comparison that the project invites becomes a load-time flag instead of a five-minute corpus rebuild.
  2. The search interface can display real words in result snippets. A snippet reading aug gener looks broken to a user; augmented generation does not.
  3. Error analysis for the written report stays readable.
  4. If the team later switches to a different stemmer, only the load step changes.

Stemming is applied on the way out of the file:

from Preprocessing import load_corpus, load_queries

docs    = load_corpus("paper", stem=True)     # yields (doc_id, tokens)
queries = load_queries("study", stem=True)

Doing this repeatedly is cheap. The corpus contains on the order of a hundred million tokens but only a few hundred thousand distinct words, so stem_tokens() memoizes each distinct word the first time it is seen and reuses the answer thereafter.

The one rule that must not be broken

Pass the same stem= value to load_corpus and load_queries. If the documents are stemmed and the queries are not, query terms stop lining up with document terms, and the model produces poor results with no error message to explain why.

5Testing, and the bugs it found

A unit test suite (test_preprocessing.py, 60 tests, standard-library unittest only) was written against the pipeline. Writing and running it exposed four defects that were not visible from reading the code.

The property that mattered

A stemmer has exactly one job: every form of a word must reduce to the same stem. A stemmer that maps variants to different strings is worse than no stemmer at all, because it actively breaks matches that plain string comparison would have found. The tests were therefore written to assert that families collapse, rather than to assert individual outputs:

stems = {simple_stem(w) for w in ("model", "models", "modeling", "modeled")}
self.assertEqual(len(stems), 1)

This formulation is what surfaced three of the four defects. Asserting stem("models") == "model" would have passed while the underlying inconsistency remained.

Defects found

DefectObserved behaviourFound byResolution
Words ending in ss address → addres, but addresses → address Writing the tests Plural rules reordered; ss endings left intact.
Words ending in y study → study, but studies → stud Writing the tests y → i applied after the -ing/-ed step.
Newline inside a paper title paper_titles.tsv wrote three rows for two papers, misaligning every reader Running the tests clean_field() strips tabs, newlines and carriage returns.
Over-aggressive -ment rule document → docu; augmented → aug Real-data smoke test Derivational suffixes require a five-character remaining stem.
Why the smoke test mattered

The -ment defect was invisible in the unit tests because no test happened to use an affected word. It appeared only when real Study queries were run through the pipeline and the output contained the token aug. Synthetic tests and real-data inspection catch different classes of problem; both were needed.

Documented limitations

Not every inconsistency is fixable with a simplified stemmer. Where a limitation is inherent, it is recorded as a passing test rather than hidden, so that it is visible during error analysis instead of being rediscovered later:

def test_known_limitation_embed(self):
    # A word whose own spelling ends in "ed" gets shortened
    # ("embed" -> "emb") while "embedding" stops at "embed".
    # The real Porter algorithm behaves the same way here.
    self.assertNotEqual(P.simple_stem("embed"), P.simple_stem("embedding"))

Reading a collection

Models should use the loader functions rather than parsing the files directly, so that the stemming setting is applied consistently on both sides:

from Preprocessing import load_corpus, load_queries, load_titles

# Build an inverted index in a single streaming pass.
index = {}
for doc_id, tokens in load_corpus("paragraph", stem=True):
    for term in tokens:
        index.setdefault(term, []).append(doc_id)

queries = load_queries("study", stem=True)   # [(qid, tokens), ...]
titles  = load_titles()                      # {paper_id: (title, abstract)}
FunctionReturnsNotes
load_corpus(level, stem) Generator of (doc_id, tokens) level is "paper" or "paragraph". A generator rather than a list, because holding 2.3 million documents in memory at once is unnecessary for a single-pass index build.
load_queries(name, stem) List of (qid, tokens) name is "study", "test" or "train".
load_titles() {paper_id: (title, abstract)} For rendering search results in the interface.
preprocess(text, stem) List of words For live queries typed into the search interface.

Notes for the modelling team

  • Paper documents are long — roughly 3,800 words on average, against about 51 for a paragraph. BM25 handles this through its b length-normalization parameter; a TF-IDF implementation needs explicit length normalization, or long papers will dominate every ranking regardless of relevance.
  • A small number of documents are empty — approximately 0.2% of paragraphs reduce to zero words after cleaning, almost all of them pure-mathematics paragraphs. They are still written to the file so that identifiers stay complete, and load_corpus returns an empty list for them. Skip them, or length normalization divides by zero.
  • Use the same function for live queries — the search interface must call Preprocessing.preprocess() on whatever the user types, with the same stem value used to build the index. Re-implementing the cleaning in the interface layer reintroduces exactly the mismatch the shared function exists to prevent.

7Running it

# Build every output file (approximately 5 minutes)
python Preprocessing.py

# Run the test suite
python -m unittest test_preprocessing -v

Setting LIMIT at the top of Preprocessing.py to a small number processes only the first N papers, which is useful for checking the output format without waiting for a full build. Corpus statistics are written to processed/build_info.txt at the end of every run.

Query 3 — Is the abstract duplicated inside the paragraphs?
files = sorted(glob.glob('JSON Files/*.json'))
random.seed(7); samp = random.sample(files, 300)

dup = 0; total = 0
for f in samp:
    d = json.load(open(f, encoding='utf-8'))
    paras = d.get('paragraphs', {})
    if not paras: continue
    total += 1
    first_key = next(iter(paras))
    a  = (d.get('abstract','') or '').strip()
    p1 = (paras[first_key] or '').strip()

      % (dup, total, 100 * dup / total))
abstract == first paragraph: 244 / 300 papers (81%)
Found a real defect. Confirmed that paper-level documents were counting every abstract term twice in 81% of papers. This was not visible from reading the code or from any unit test; it required looking at the corpus itself.
Query 4 — Does cleaning destroy any judged-relevant paragraph?
judged = {}
for line in open('Study_paragraph_qrel.tsv', encoding='utf-8'):
    qid, _, pid, rel = line.split()
    judged.setdefault(pid.split('_')[0], []).append((pid, int(rel)))

empty = []; checked = 0; missing = 0
for paper_id, items in judged.items():
    try:
        d = json.load(open('JSON Files/%s.json' % paper_id, encoding='utf-8'))
    except FileNotFoundError:
        missing += len(items); continue
    paras = d.get('paragraphs', {})
    for pid, rel in items:
        if pid not in paras:
            missing += 1; continue
        checked += 1
        if not P.preprocess(paras[pid]):
            empty.append((pid, rel))
print('judged paragraphs checked:', checked)
print('judged paragraphs missing from corpus:', missing)
print('judged paragraphs that clean to ZERO tokens:', len(empty))
judged paragraphs checked: 728 judged paragraphs missing from corpus: 0 judged paragraphs that clean to ZERO tokens: 0
Confirmed the pipeline is safe. Aggressive cleaning could in principle remove a relevant document from reach entirely, capping recall no matter how good the ranking model is. This check shows it does not happen, and it is a result worth stating in the written report.

9Summary

The preprocessing component converts 34,308 paper files into two tokenized document collections and three tokenized query sets, using a single shared cleaning function so that documents and queries are guaranteed to be treated identically. The saved files hold cleaned but unstemmed words, which keeps stemming a reversible, load-time choice rather than a decision baked irreversibly into the data.

Two findings are worth carrying into the written report. The first is the duplicated abstract: 87% of papers repeat their abstract as the first paragraph, and counting both copies inflates term frequency on the most topical words in the collection. The second is the testing work — four defects were found, three of which were violations of a single property, that every form of a word must reduce to the same stem, and none of which produced an error message. They degraded retrieval quality silently, which is precisely the failure mode that makes a correctly implemented model appear to perform poorly.
